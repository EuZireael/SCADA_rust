# Что прошивка делает с записанным значением

Для разработчика монитора и скриптов. **`APPLIED` в результате команды значит «прошивка приняла команду (код 0)», а не
«значение изменилось».** Прошивка ptusa (эмулятор мойки с проектом BN1-МСА1) принимает почти любую команду, а потом
программа ПЛК сама решает, что стоит в поле. Ниже — что именно, снято с прошивки (2026-10-05, проект BN1-CIP1) и
воспроизведено в Rust-симуляторе (`simulator/`) один в один.

## Как снято

Для каждого из 1816 записываемых числовых каналов станции: прочитать значение, записать другое (`set_cmd`), через
0,45 с прочитать снимок, вернуть как было. Затем повторить в ручном режиме (`M=1`) для приборов с режимом, понаблюдать за
возвратом в автоматику. Повторяется командой `simulator conformance` (см. ниже).

## Результат

| | Каналов | Что происходит |
|---|---|---|
| **Держится** | 1675 | значение принято и стоит |
| **Только в ручном режиме** (`M=1`) | 18 | в автоматическом режиме команда принимается (код 0), но значение остаётся за программой; при `M=1` действует и держится; **вернули `M=0` — значение сразу возвращается к тому, что считает программа**. Главные клапаны линий `LINE1V0`, `LINE2V0`, `LINE3V0` (воды из сети), 12 виртуальных выходов `LINE#DO#`, 3 сторожевых таймера `LINE#WATCHDOG#`; остальные 62 клапана держат команду и в автоматическом режиме |
| **Игнорируется** | 107 | команда принимается, значение не меняется ни в каком режиме: его считает программа или железо — обратная связь клапанов (`NAMUR_ST`, `OPENED`, `CLOSED`), модули питания `CAB#G#` (токи, напряжение, `ST`, `ERR`…), уровень `LT#.CLEVEL`, температура `LINE#QT#.T`, лампы `HLA`, у технологических объектов `OBJECT#` — `STATE`, `OPER`, `CMD` (регистр команд: прошивка его «съедает»), `REC_PAR`, часть `RT_PAR_F`; `SYSTEM.CMD`, `SYSTEM.NODEENABLED` |
| **Целое** | 16 | значение принимается и держится, но хранится целым: `7.5` становится `7`. `OBJECT#.RT_PAR_F[12]`, обороты `LINE#M#.RPM`, счётчики `ABS_V`, параметры `SYSTEM` (`WASH_VALVE_*`, `P_RESTRICTIONS_*`, `P_AUTO_PAUSE_OPER_ON_DEV_ERR`) |

Остальное, что стоит знать:

- **Одна запись `M=1` клапан не открывает** — режим и состояние пишутся двумя командами (`M`, затем `ST`).
- **Состояние (`ST` клапана)**: целая часть, отличная от нуля, даёт 1 (`7` → открыт), `0.5` → закрыт.
- **Код ответа на команду**: неизвестный прибор — 1; не число (`'abc'`) и не команда — 1 (ошибка Lua); **неизвестное поле
  известного прибора — 0** (принято и проигнорировано); поле «для чтения» — 0.
- Все 1816 записей вернули код 0 — **шлюз не может отличить «действует» от «проигнорировано» по ответу**.
- Файл ограничений проекта (`main.restrictions.lua`) пуст: логика в самой программе станции.

## Что это значит для монитора

- Оператор нажал «открыть» на `LINE1V0` в автоматическом режиме → `APPLIED`, клапан закрыт. Чтобы знать наверняка, смотрите
  значение в телеметрии после команды (оно приходит со следующим опросом) или переводите прибор в ручной режим.
- Запись в поля из строки «Игнорируется» бессмысленна: результат всегда `APPLIED`, значение прежнее.
- Шлюз может сам проверять эффект записи (прочитать значение обратно и сказать `success=false`) — это отдельное
  решение (статус результата менять в интерфейсе монитора), в шлюзе сейчас не включено.

## Как это воспроизведено в симуляторе

В `simulator/config/replay_config.yaml` у тега (только записываемые):

```yaml
- {name: "385", device: "LINE1V0", field: "ST", ..., write_state: true, write_requires: {field: M, equals: 1}}  # только при M=1
- {name: "...", device: "LT1", field: "CLEVEL", ..., write: ignore}        # принимается, не меняет
- {name: "...", device: "OBJECT1", field: "RT_PAR_F[12]", ..., write_int: true}   # целое
```

Правила одинаковы для OPC UA, PAC и Modbus-регистров симулятора (запись OPC UA проходит со статусом Good и не
меняет значение). Протокол PAC отвечает как прошивка (коды выше).

**Проверка соответствия** — `simulator conformance [host] [port] [config]` — идёт по driver-master и сверяет записанное
с конфигурацией у любого PAC: на симуляторе её запускает CI, на настоящей прошивке её запускают руками, чтобы убедиться,
что правила в конфигурации до сих пор верны. Результат на прошивке мойки: 126 записываемых PAC-тегов конфигурации — **81
соответствуют, 45 пропущено (таких каналов нет в реальном проекте), расхождений 0**, коды ответов совпадают.

```sh
scripts/ptusa_emulator.sh <проект ПЛК>                  # прошивка на :10100
simulator/target/release/simulator conformance 127.0.0.1 10100 simulator/config/replay_config.yaml
```
