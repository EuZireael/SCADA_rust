# Телеметрия «по исключению» (Rust-шлюз)

Контракт публикации значений в Kafka, на который опирается монитор (`scada-editor-backend`,
сервис `runtime`). Реализован в `src/filter.rs`, подключён в `src/telemetry.rs`. Правила и имена
настроек те же, что у Java-шлюза (ветка `feat/telemetry-by-exception`), — монитору менять нечего.

## Правила публикации значения тега

Значение тега уходит в Kafka, если выполнено хотя бы одно (проверяются по порядку):

1. **Первое значение** тега после старта шлюза.
2. **Сменилось качество** (GOOD ↔ BAD) — обрыв и восстановление связи публикуются сразу.
3. **Прошло `full-resend-ms`** с последней публикации тега — полная отправка: неизменившееся
   значение повторяется, чтобы монитор знал, что тег жив, и после своего перезапуска получил
   значения всех тегов не дольше чем за этот период.
4. Если с последней публикации прошло меньше `min-interval-ms` — не публиковать (антидребезг; 0 —
   выключено). Отрезанное окном изменение не теряется: оно уйдёт первым опросом после окна.
5. **Значение изменилось** относительно последнего *опубликованного* (не предыдущего опроса):
   числа — `|новое − опубликованное| > max(deadband, |опубликованное|·deadband-percent/100)`
   (при нулевой зоне — любое отличие, `NaN == NaN`); не числа — на равенство.

Интервалы считаются по часам шлюза, а не по метке источника (OPC UA не двигает метку, пока
значение стоит). BAD-кадр без `GATEWAY_SEND_BAD_FRAMES` не публикуется и не запоминается. Формат
сообщения, ключ и топик не меняются.

## Настройки

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `GATEWAY_PUBLISH_ENABLED` | `true` | `false` — прежнее поведение: каждый тег каждый цикл |
| `GATEWAY_PUBLISH_DEADBAND` | `0` | абсолютная зона |
| `GATEWAY_PUBLISH_DEADBAND_PERCENT` | `0` | относительная зона, % |
| `GATEWAY_PUBLISH_MIN_INTERVAL_MS` | `0` | не чаще раза в N мс на тег |
| `GATEWAY_PUBLISH_FULL_RESEND_MS` | `30000` | полная отправка |
| `GATEWAY_HISTORY_DEADBAND` / `_DEADBAND_PERCENT` / `_MIN_INTERVAL_MS` / `_MAX_INTERVAL_MS` | `0 / 0 / 0 / 600000` | фильтр локальной истории (`GATEWAY_PERSIST_TELEMETRY=true`) |

Для истории тег переопределяет поля блоком в `controllers.yaml`:
`history: {deadband: 0.5, deadbandPercent: 1, minIntervalMs: 60000, maxIntervalMs: 600000}`
(колонки `tags.history_*`). На публикацию в Kafka этот блок не влияет.

`runtime.telemetry.max-silence-ms` монитора (40 с) должен быть **больше** `full-resend-ms`.

## Сочетание с горячим резервированием

Публикует только активный экземпляр; резерв опрашивает контроллеры, но молчит и не «запоминает»
неотправленное. При получении лидерства состояние фильтров сбрасывается (эпоха
`Leadership::activations`), поэтому новый активный первым же циклом отправляет все теги — монитор
после переключения не ждёт полной отправки. (В Java-шлюзе фильтр стоит выше гейта продюсера, и
резерв «запоминает» значения, которые на самом деле никуда не ушли.)

## Находки нагрузочного стенда Java-шлюза и как они закрыты

| Находка | В Rust |
|---|---|
| Конфиг тегов через окружение Spring съедает 1,5 ГБ | собственный разбор YAML (`serde_yaml_ng`), 54 800 тегов ≈ 125 МБ RSS всего процесса |
| История пишется на треде опроса, пул БД исчерпан | история — через ограниченную очередь и пакетную вставку (`UNNEST`) в отдельной задаче; при переполнении сбрасывается с метрикой `scada_telemetry_rows_dropped_total` |
| Один замок на `host:port` в PAC | соединение PAC на контроллер |
| Lua-снимок PAC компилируется заново | снимок исполняется в стейте соединения; на 1834 каналах разбор ≈ 0,2 мс/цикл (при необходимости — разбор без Lua, см. «Что не сделано») |

## Измерения

Стенд из контракта: 20 OPC UA-серверов × 2740 узлов (`loadtest/loadsim`), опрос 2 с, треть узлов
меняется каждую секунду, фильтр публикации с нулевой зоной (худший случай: любое отличие — это
сообщение). Шлюз — нативный release-процесс на 16-ядерной машине, Kafka и PostgreSQL в docker.

| | Rust-шлюз |
|---|---|
| Сообщений в Kafka | 18 280/с (все изменения), подавлено ≈ 9 100/с |
| Цикл опроса контроллера (2740 тегов) | p100 < 100 мс при периоде 2 с; пропущенных циклов 0 |
| Обработка цикла (скрипты, фильтры, алармы, сборка сообщений) | ≈ 28 мс на 2740 тегов |
| CPU | ≈ 25–27 % одного ядра (включая запись 18 280 строк/с истории в PostgreSQL) |
| Память (RSS) | ≈ 125 МБ |
| Ошибки Kafka / потерянные строки истории | 0 / 0 |

Повторить: `loadtest/README.md`.

## Что не сделано

- Разбор снимка PAC без Lua (п. 4 контракта): на реальной станции вклад пренебрежим
  (≈ 0,2 мс на цикл из 1834 тегов); имеет смысл только для PAC в сотни тысяч полей.
